# Motion Playground · 待验收原型

回答一个问题：连续新增、跨列和并行改状态时，哪套原生动画更容易追踪且顺滑？

这是可直接操作的独立 MyGo App，不以录屏代替验收。三个候选使用同一布局、相同 API 时序和真实 SSE；不接触正式看板的数据。

| 方案 | 动画 | 用于比较 |
| --- | --- | --- |
| A · 快速缓出 | 260ms ease-out | 快速、明确的落位 |
| B · 柔和弹簧 | 420ms、回弹 0.04 | 平顺衔接、轻微回弹 |
| C · 错峰弹簧 | 480ms、回弹 0.12、每卡 55ms 视觉错峰 | 更明显的节奏与跟随感 |

## 直接使用

打开 `build/playground/darwin-arm64/Taskboard Motion Playground.app`。在顶栏选择方案，再点“播放同一场景”；可点“停止”后换方案重播。

每次播放都通过该 App 独立启动的 HTTP API：清理临时场景 → 连续新增三卡 → 错峰经过进行中、评审、完成 → 两卡同时回到不同状态 → 再次完成。创建间隔固定 180ms、API 移动间隔固定 120ms，三套方案不改变请求时序。场景全部使用临时数据库，只保留到本机临时目录的生命周期；不读取正式数据库，退出不会自动删除任何目录。

## 重新构建

在仓库根目录执行：

```bash
GOFLAGS=-tags=motionplayground mygo build -skip-dmg playground
```

或直接运行：

```bash
go run -tags motionplayground ./cmd/taskboard
```

可选 `--variant A` / `B` / `C`，`--autoplay` 自动播放一次，`--compare` 自动顺次播放三个方案。

## 隔离与验收门

生产入口 `main.go` 与 `motion_default.go` 使用 `!motionplayground`；实验入口、控制栏、参数和上层移动卡片逻辑使用 `motionplayground`。普通构建不会包含实验控制栏、临时服务或三套候选动画。主窗口和 Playground 的 bundle identifier 也不同，可以独立打开。

当前状态：**默认 B · 柔和弹簧，等待正式合入验收，未合入生产动效。**

2026-10-25 最新选择：用户指定 **B · 柔和弹簧为默认方案**，仍待正式合入验收。拖放落位修复也只留在 Playground：记录鼠标抓取偏移，从松手时拖动副本的窗口位置接续动画；目标占位不再参与位置动画，避免双重运动；列内指针坐标先转换为窗口坐标；乐观排序与服务的落位顺序对齐，避免 SSE 确认后二次改道。逐帧回归覆盖跨列、反向拖动、同列排序和空列落位。

验收重点：连续创建是否有节奏；三卡同时移动时是否能看清每张的起点和终点；中途改状态是否跳位；停止和重播是否可靠。选定后只迁入需要的最小实现，再跑正式窗口验证。

拖起时源卡退出正常布局，后续卡片以当前方案的动画收拢；目标列显示与被拖卡片等高、无文字的淡色占位块，邻卡实时让位。占位索引按排除源卡和占位块的自然布局计算，不追逐运动中的卡片，因此悬停时不会反复换位。跨列与同列排序共用这一预览；空列隐藏空态文案，展示占位块。释放才通过 API 提交预览顺序；取消或拖出有效区域释放，从指针位置平滑返回原位。该调整只在 Playground 中启用，替代之前保留原位空洞的方案。

拖入列时的蓝框只改变颜色，不改变几何：始终预留 2 DIP 透明边框，并将列内边距相应减少 2 DIP，保持原内容缩进。回归检查覆盖有卡片和空列，悬停前后列头与输入框的位置、宽度完全一致。
