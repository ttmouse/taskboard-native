# 看板共享方案：先支持个人多设备，再扩展多人协同

状态：方案稿，供产品与技术评审；本文不代表多人能力已经实现。

## 结论

如果当前只要让同一个人在多台电脑上使用，组织协作方案仍然过大。建议首发改成“一个个人账号，多台设备，共用一个远端工作区”；组织、邀请、成员目录和项目权限全部后置。这个需求的核心是可靠的数据同步与账户登录，不是权限矩阵。

多设备仍必须由一个中心服务端持有权威数据。所有桌面端通过认证 API 访问同一个服务；服务端在自己的本机磁盘上持有数据库。禁止把 SQLite 文件放进网盘同步、网络文件系统或让多台电脑直接打开它。现有本地单机模式继续保留；首版在线使用，断线重连，不做离线双向合并。

## 首发边界：先解决个人多设备

首版只回答一个问题：同一用户能否在两台及以上电脑登录同一账号，看到同一份项目、任务、评论和状态变化。

- 一个个人账号只有一个默认远端工作区，账号下所有已授权设备访问相同项目；没有组织、邀请、成员表或项目 ACL。
- 最快的个人试用方式：在一台常开电脑部署服务端，SQLite 只保存在这台电脑的本地磁盘；其他电脑经私有 VPN 访问。服务端需增加认证并限制网络暴露，不能只依赖“知道地址”。
- 面向正式产品：部署托管服务，用户登录同一个个人账号，从任何设备访问；服务端数据库仍是唯一权威副本。初期可单服务单实例；数据库选型由托管和备份方案决定，不必为了个人试用先引入多租户和分布式设施。
- 沿用现有任务版本冲突、SSE 和断线快照；冲突明确提示，不静默覆盖。首版不做离线编辑合并、设备间数据库同步或复杂审计。
- 现有本地单机项目可以继续本地使用。导入远端工作区先提供明确的一次性迁移或从空远端开始，不做持续双向同步。
- CLI/MCP、组织邀请、多人角色和团队隔离不是个人多设备首发条件；它们在需要多个人使用时再加。

明确的代价：中心服务不可用时，多设备不能读写；离线时只读本机模式数据，不自动与远端合并。若优先解决的是“马上在自己的几台电脑使用”，先用私有 VPN + 一台常开主机即可验证需求；若要让用户普遍开箱可用，再做托管服务和个人账号。

### Tailscale 是否适合作为个人多设备的连接方式

可以考虑，适合作为个人试用时的私有网络入口；它解决的是“其他设备如何安全连到唯一服务端”，不负责同步或合并各设备上的数据库。仍由一台常开设备持有 SQLite，其他设备通过 API 访问这份权威数据。Tailscale Serve 可将服务端本机的 `127.0.0.1` 端口代理到 tailnet 内的 HTTPS 地址；Serve 仅对 tailnet 开放，并受 tailnet grants/ACL 规则限制。必须显式检查策略，确保只有自己的设备可访问；不要假设启用 Serve 就自动限制为本人设备，也不要使用对公网开放的 Funnel。

但这不是装上 Tailscale 就能直接用现有桌面版：按当前仓库代码，GUI 启动时会在本机启动服务并连接该服务；客户端地址也按 `http://host:port` 处理，没有连接远端 HTTPS 服务的配置。因此要让多台电脑的 GUI 共用同一看板，还需增加“连接已有远端服务”的客户端模式/地址配置，并确保客户端只访问服务端 API，不在每台设备启动独立写库服务。该配置完成前，Tailscale 只能作为网络方案候选，不能视为已打通的多设备体验。

建议实施顺序：先保持服务端只监听 `127.0.0.1`，由 Tailscale Serve 代理本地端口；在 tailnet policy 中只授权自己的设备访问，不把整个组织默认开放。个人自用试点可以暂以 tailnet 设备授权作为网络入口，但它不提供看板内的账户身份；任何获准连接的设备都能以看板现有权限读写数据。正式多设备版本仍应实现应用层登录与设备撤销。若加入其他使用者，或需要按应用用户区分看板权限，必须实现应用层身份认证与授权。服务端关机或 Tailscale 不可用时，远端设备无法访问；备份和服务端持续在线仍由使用者负责。

依据： [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve) 说明可将本机服务提供给 tailnet，并受访问控制策略约束；[Access control](https://tailscale.com/docs/features/access-control) 说明 tailnet grants/ACL 管理设备间访问。官方文档查阅日期：2026-10-30。

## 目标与边界

- 公司成员能看到被授权的组织和项目，并实时看到任务、列、评论等变更。
- 首发是一人账号的多设备访问；多人组织成员、邀请和项目级角色属于后续目标。
- 用户身份可稳定关联评论、任务操作和审计记录；撤权后新请求立即失去访问权。
- 保留代理 CLI/MCP 能力，但所有代理写入都继承明确用户或服务身份及其项目权限。
- 先支持在线协作和断线后重连快照；首版不支持离线编辑队列、合并冲突、跨组织共享链接、访客匿名编辑、细粒度字段权限或企业 SSO。

## 组织模型选择

| 模型 | 优点 | 代价 / 风险 | 结论 |
| --- | --- | --- | --- |
| 仅项目邀请 | 概念少，适合临时小组 | 同一公司成员、账单、安全策略散落在各项目；重复邀请与离职回收困难 | 不作为主模型 |
| 仅组织成员，所有项目默认可见 | 加入组织后即能协作，管理直观 | 新项目容易意外暴露；大组织无法按团队隔离 | 只适合小型封闭组织，可作为组织策略选项但默认关闭 |
| 组织成员 + 项目成员 | 公司级管理与项目最小权限兼顾；可在组织内按项目隔离 | 多一层授权关系，需要明确继承规则 | 目标形态；首版暂缓 |

多人组织阶段的授权规则必须简单且无歧义：组织 Owner/Admin 可访问和管理组织内全部项目；普通组织成员只能访问显式加入的项目；项目角色决定该项目内可读、可写和管理成员的能力。若多人试点先采用组织全员可见，应明确接受该边界，不要同时实现两套默认策略。

## 角色与权限

多人组织阶段可采用以下固定角色；个人多设备阶段没有组织成员角色：

| 角色 | 范围 | 能力 |
| --- | --- | --- |
| 组织 Owner | 组织 | 删除/转让组织、账单和全部管理权限；至少保留一名 Owner |
| 组织 Admin | 组织 | 邀请/移除成员、创建/归档项目、查看和管理所有项目 |
| 组织 Member | 组织 | 组织目录可见；无项目自动访问权 |
| Project Admin | 单项目 | 看板读写、项目设置、管理项目成员和角色 |
| Editor | 单项目 | 查看并创建/编辑/移动任务、评论；不能管理成员或删除项目 |
| Viewer | 单项目 | 只读看板与评论；不能写任务、评论或发起执行 |

服务端对每个 API 请求、SSE 订阅、图片读取、CLI/MCP 工具调用执行同一授权策略。隐藏界面入口不是权限控制。管理员移除成员或撤销项目角色时，已有 SSE 连接应关闭或重新授权；已签发短期访问令牌按短时效设计，刷新令牌可立即撤销。所有写操作保存 `actor_user_id`，代理另记 `actor_type` 与 `agent_name`，不能把代理名当作用户身份。

## 架构与数据

### 部署形态

```text
桌面端 / tb CLI / MCP
        │ HTTPS + 用户认证
        ▼
Taskboard API 服务（授权、业务校验、审计、SSE）
        │ 单写事务（多实例时再加事件 outbox）
        ├── PostgreSQL（共享权威数据）
        └── 对象存储（图片等附件，可后续启用）
```

- 当前 SQLite Store 保持本地模式；新增共享后端接口边界，避免 UI/CLI/MCP 直接依赖 SQL。远端模式使用 PostgreSQL 和服务端事务，不把 SQLite 文件放在共享盘。
- 所有 API 首先从已验证的身份上下文取得 `user_id`，再解析组织/项目授权；请求体中的 `organizationId`、`projectId` 仅是资源定位符，不能作为授权凭据。
- 数据库记录必须带 `organization_id`，项目唯一属于一个组织。查询与写入均以组织/项目授权过滤；外键和唯一约束也纳入组织范围，避免跨租户引用。
- SSE 按授权项目订阅。事件由数据库事务提交后的 outbox 发布，避免“数据已写但进程在广播前崩溃”导致长期漏事件。客户端重连先取授权范围内快照，再接收后续事件；事件序号按组织或项目作用域递增。
- 现有 task version 乐观并发机制保留。并发编辑返回 409 和当前版本；评论追加仍是独立动作。第一版不做 CRDT 或自动合并。

### 建议核心表（分期落地）

- `users(id, email_normalized, display_name, status, created_at)`
- `organizations(id, name, slug, created_by, created_at)`
- `organization_memberships(organization_id, user_id, role, status, joined_at)`；唯一键 `(organization_id, user_id)`
- `invitations(id, organization_id, email_normalized, role, token_hash, expires_at, accepted_at, invited_by)`；只存邀请 token 的哈希
- `projects` 增加 `organization_id`、`created_by`；迁移期间本地项目可暂时为空组织，完成归属前只允许本地模式读取
- `project_memberships(project_id, user_id, role, added_by, created_at)`；唯一键 `(project_id, user_id)`；这是后续项目隔离阶段才需要的表
- `tasks/comments` 增加规范化的 `updated_by_user_id` / `author_user_id`；保留展示用 agent 名称，但不再把它当作账户
- `audit_events(organization_id, project_id, actor_user_id, action, resource_type, resource_id, request_id, created_at, metadata)`；metadata 设字段白名单，不写 token、正文敏感信息
- `outbox_events(id, organization_id, project_id, sequence, event_type, payload, created_at, published_at)`

目标形态中项目成员可通过组织成员外键约束；删除组织成员时，在事务中撤销其全部项目成员关系及未使用邀请。首版没有项目成员表。业务数据默认软删除/归档并按产品保留策略清理；组织删除必须二次确认，导出、保留期和可恢复期明确后才能实现。

## 邀请与协作流程（多人组织阶段）

1. 用户注册或登录后创建组织；创建者成为 Owner。个人多设备阶段只需同一账号登录多个设备，不创建组织。
2. Owner/Admin 按邮箱邀请成员，可选择普通组织角色；邀请具备到期时间、单次使用、撤销能力。首版不自动按邮箱域名把人加入组织。
3. 项目隔离尚未启用时，组织成员创建的项目对组织全员可见；创建者成为组织 Owner 或由 Owner 管理项目。
4. 待项目隔离阶段启用后，Project Admin 才能从组织成员中添加 Editor/Viewer。邀请非组织成员时，先接受组织邀请，再接受项目授权。
5. 桌面端通过组织/项目切换器切换范围。所有页面、搜索、全局视图都只聚合当前身份有权访问的项目。
6. 离职或移除时禁用用户会话、撤销组织成员关系（后续还要撤销其项目成员关系）、停止其 SSE，并保留历史操作的原始 actor 关联（展示为“已停用成员”而非抹去审计记录）。

## API 与客户端变化

多人组织阶段的认证 API 至少包括：

- `GET/POST /api/organizations`、`GET/PATCH /api/organizations/{id}`
- `GET/POST /api/organizations/{id}/members`、成员角色更新/移除
- `POST /api/organizations/{id}/invitations`、接受/撤销邀请
- `GET/POST /api/projects` 支持组织范围；项目成员的列出、添加、角色更新、移除
- `GET /api/me` 返回用户及其可访问组织/项目摘要
- SSE 订阅校验身份及项目访问范围，并在成员撤权后终止无权订阅

个人多设备阶段只需要个人账号登录/设备撤销、`/api/me` 或等效会话接口，以及现有看板 API 的身份校验；组织和成员 API 留到多人阶段。HTTP 契约和凭据管理仍需先定义清楚，不能以“先简化”为由开放无认证的远端接口。

现有无认证本机 API 不能直接暴露到公网。远端服务要求 HTTPS、认证和服务端授权；本机模式维持默认环回地址。API/CLI/MCP 契约需先在 `docs/contracts.md` 明确认证头/会话、身份透传、错误码、SSE 和兼容策略，再实施。CLI 提供显式登录/凭据管理及组织/项目选择；凭据存 OS Keychain，禁止写入配置明文、日志、任务评论或命令回显。MCP 使用每个用户自己的短期凭据或受限服务身份，并且其权限不高于授权用户。

## 本地数据与迁移（后续阶段）

本地模式和组织共享模式是两种明确的数据权威模式，不能静默同步：

1. 新建本地组织时不改动既有本地项目。
2. 用户主动选择“迁移到组织”后，先创建远端项目并上传项目、列、任务、评论、附件及审计所需的作者映射；保留原始 ID 或写确定性的 ID 映射，避免评论/附件引用断裂。
3. 迁移前生成一致性快照并校验数量、引用关系与附件摘要；成功后将本地项目标记为只读归档副本，再切换客户端到远端项目。
4. 任一步失败可重试或放弃，不能清空本地源数据。迁移期间禁止两边同时写；切换时显示明确来源和目标。
5. 第一版不承诺将在线组织项目导出后继续双向同步到 SQLite；导出备份与恢复是后续独立能力。

## 安全、可靠性与运营要求

- 密码使用成熟身份提供方或经审计的密码哈希方案；优先采用成熟 OIDC 服务，避免自研密码找回、MFA 和邮件投递。MFA、SAML/SCIM 属后续企业能力。
- 每个租户查询都做服务端授权；增加跨组织越权的负向测试，包括猜 ID、搜索、附件 URL、SSE 和 MCP。
- API 限流登录/邀请/写入；防 CSRF（若用 Cookie）、防重放、参数校验；秘密只进加密密钥管理，不进日志。
- 审计成员变更、权限变更、登录、导出和高风险删除；设置保留期限与组织管理员可见范围。
- 备份需加密并定期验证恢复；定义 RPO/RTO 后再承诺 SLA。PostgreSQL 连接、迁移、outbox 堆积、SSE 连接和授权拒绝应有指标与告警。
- 组织间搜索、全局看板、计数和排序也要执行同样的数据范围过滤，避免通过数量或标题泄露其他租户信息。

## 分阶段交付

### 阶段 0：验证个人使用方式

确认只在个人设备之间共享，还是近期就要多人协作；确认用户是否接受托管，或愿意维护一台常开电脑和私有 VPN。不要因为远期团队场景，先造组织权限系统。

### 阶段 1：个人多设备版

先让一个服务端实例持有数据库，桌面客户端登录同一账号并通过认证 API 访问；实现远端访问保护、任务/评论读写、SSE、冲突提示、设备撤销和可恢复备份。可先用私有 VPN 内的小范围部署验证，再决定是否托管化。现有本地模式保持独立可用。

### 阶段 2：多人组织协作

多个用户确实需要共享后，再加入组织、成员邀请与撤权、组织级隔离、审计以及必要的 CLI/MCP 身份链路。若试点需要不同团队互相看不到项目，再增加项目成员表和角色。多实例 outbox、企业身份和 SLA 按实际运营需要增加。

### 阶段 3：企业治理与迁移

再实现本地项目迁移工具、Viewer/自定义角色、域自动加入、企业 SSO/SCIM、导出/删除工作流与容量告警。根据客户需求决定托管或自托管，不要在首发前同时承诺两种部署。

## 验收标准

### 个人多设备首版必须满足

- 只有已认证且已授权的个人账号设备能访问该账号数据；未认证请求和其他账号不能通过 API、搜索、任务 ID、附件地址或 SSE 访问。
- 两台在线设备对同一项目的任务创建、移动、评论能实时互见；断线重连通过快照恢复；并发编辑明确报告版本冲突，不静默丢数据。
- 用户可以撤销丢失设备的访问；中心数据库有加密备份并完成恢复演练。
- 本地单用户模式及原 SQLite 数据保持可用；远端共享模式不要求各设备直接读写该 SQLite 文件。

### 后续多人组织阶段增加

- 不同组织之间数据隔离；移除成员后 API 和现有 SSE 都拒绝访问。
- 若启用项目隔离，组织 Member 不能读取未加入的项目；Viewer 的任何写接口返回明确 403。
- 本地迁移失败不损坏源数据，可重试或取消；角色变更和高风险数据操作可审计。
- 明确 RPO/RTO 和数据保留期限后，才对外承诺 SLA。

## 主要风险与尚待决策

1. **部署和责任边界**：托管云、自托管或两者并行会决定升级、备份、账单和支持成本。MVP 应只选一种受支持的远端部署，避免同时建设两套运维路径。
2. **本地到云的迁移**：用户会担心数据复制和权限映射。必须有预览、校验、回滚和原地保留，不应自动上传。
3. **过度建设权限系统**：首版若加入自定义角色、域自动加入、访客、跨组织共享和细粒度字段权限，会显著扩大测试矩阵；先验证组织+项目两层角色是否覆盖真实团队。
4. **桌面应用与账户安全**：远端 API 使本地环回服务的信任假设失效，CLI/MCP、附件和执行 Agent 都必须纳入身份链路，不能只给 GUI 加登录页。
5. **可用性承诺**：SSE 和 API 服务需要持续运维。若团队暂时不准备承担数据库、备份、升级、监控和事件响应，就先提供受控自托管服务，而不要把共享 SQLite 当成低成本捷径。

建议下一步先按个人多设备验证：选一台常开电脑作为唯一服务端和数据库持有者，用私有 VPN 让其他设备连接，补上认证、设备撤销和可恢复备份。验证稳定且确实需要随时随地使用后，再迁移到托管远端服务；只有再出现其他真实用户需要加入时，才启动组织和项目权限设计。
