## 现状与证据

删除含直接回复的评论是一个逻辑操作，成功时要把所有直接回复提升为一级并删除父评论。SQLite 语句逐条提交，而不是全部成功后一起提交。磁盘/数据库错误或外部锁失败可使后续语句失败，导致部分提升或父评论仍在。

## 建议方向

在 Store 锁内用一个 SQLite transaction 执行所有直接回复提升与父评论删除；事务成功提交后再发布对应 comment.updated 与 comment.deleted 事件，失败时不发布任何事件。保留所有后代层级只提升直接子项的现有契约。

## 验收标准

注入事务中段失败时，数据库保持原有父子关系且没有 SSE 事件；成功时所有直接回复提升、父项删除，按契约发布完整事件序列；现有作者权限和跨任务隔离保持不变。

补充性能成本（2026-11-04）：DeleteComment 对每个直接回复单独调用一次 db.Execute 执行 UPDATE，之后再对父评论单独 DELETE；删除拥有 R 条直接回复的评论至少产生 R+1 次写 SQL 调用，且每次调用都在 Store 全局锁内。回复行和逐条 comment.updated 事件载荷已经由前置查询取得，数据库父级字段可通过一次集合 UPDATE 改写，再在事务成功后按原顺序发布每条事件；这能将 SQL 写调用从 O(R) 降到常数，同时保留逐回复事件。验收增加 0/1/大量直接回复下的 SQL 调用计数与锁持有耗时对照；事务与事件原子性仍按原验收执行。
