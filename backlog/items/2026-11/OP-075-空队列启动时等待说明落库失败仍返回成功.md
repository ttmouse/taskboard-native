## 现状与证据

Starting project auto-handoff when no eligible cards exist creates and persists a running ProjectRun. The code then adds the explanatory waiting detail but ignores persistence failure and returns success. A transient SQLite write failure can therefore produce different run details in the 202 response and durable state; after restart the explanation is lost even though the run remains enabled.

## 建议方向

Propagate or explicitly record the second SaveProjectRun failure before returning success, and keep the response aligned with durable state. If the run switch is intentionally left enabled after failure, expose an actionable persistence error and make the durable state recoverable.

## 验收标准

With an empty queue and a fault injected only into the detail update, the start response must not claim a durable waiting detail that GET/restart cannot read; outcome must clearly distinguish a persisted running run from failure to persist its explanatory state, while preserving the enabled switch semantics.
