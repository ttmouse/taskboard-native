## 现状与证据

comments 表已有全量评论读取用的 task_id/created_at 索引；写路径只需要检查目标评论是否属于该 task、作者是否匹配，添加回复时只需查 parent ID 是否同属 task。数据库行 ID 自身为主键。

## 建议方向

改用按 comment ID + task ID 的定向 SELECT/UPDATE/DELETE，并只读取写事件所需的目标评论字段；回复父级归属也做定向存在性查询。为父评论删除的直接回复查询评估 `(task_id,parent_comment_id,created_at)` 索引，避免在已缩窄到单卡后仍遍历该卡的所有评论。保持同一任务隔离和作者校验，不读取无关 comment body。

## 验收标准

针对评论很多且正文较长的任务，添加回复/编辑/删除不再加载整条评论历史；删除有少量直接回复的父评论时，查询计划按 task_id 与 parent_comment_id 定位，不扫描该任务全部评论。跨任务伪造 parent、作者不匹配、回复顺序和父评论删除后直接回复提升为顶层等语义保持一致；评估新增索引的写入和磁盘成本。
